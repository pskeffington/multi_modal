# Literature matrix: token optimization for local Qwen3.5 deployment

**Review date:** 2026-11-23  
**Target:** Qwen3.5-9B GGUF via the loopback llama.cpp router in `multi_modal`; GLM escalation stays untouched.  
**Purpose:** Evidence-ranked decisions for Codex, not a claim that a technique is already deployed or benchmarked on this host.

## Research question and evidence rules

Which mechanisms improve **(a)** true prompt/output token economy, **(b)** prefill/decode cost for the same token count, or **(c)** GPU memory/serving capacity **without compromising** task quality, structured triage, manual Codex review, source fidelity, or local-only inference?

The three outcomes are **not interchangeable**. Prompt-length reduction changes billed/logical token count; KV/prefix reuse reduces how much unchanged input is *computed again* but may leave the full prompt token count unchanged; KV quantization, batching and speculative decoding change memory/latency/throughput and do not automatically shorten the prompt or answer.

Evidence hierarchy: official Qwen model card and llama.cpp server documentation for *documented capabilities*; peer-reviewed papers for *mechanisms and original evaluation*; project source and QA report for *current repo behavior*; upstream GitHub issues/discussions for *version-sensitive risks*, never as proof of this host's behavior. No paper's reported gains should be treated as a forecast for Qwen3.5-9B GGUF on the user's GPU. Paper percentages below refer to their **own** test setups.

## Local baseline and operational constraints

- [Local client](../src/multi_modal/client.py): `LocalClient.chat()` sends non-streaming `/v1/chat/completions` with `temperature=0.1` and a `max_tokens` argument; it returns only the final content string and raises a blocker if reasoning consumes the budget without final text. It does not currently persist structured `usage`, `finish_reason`, cached-token counts, or timings for normal successful tasks.
- [Worker](../src/multi_modal/worker.py): Qwen triage has a **512** completion-token budget with a single schema repair; direct/assigned tasks have **2,048** by default. Follow-ups resend the ordered persisted conversation. Only one inference worker is active, and GLM escalation is gated by risk/complexity/confidence.
- [Store](../src/multi_modal/store.py): the initial conversation embeds any explicitly selected Git snapshot in the first user message; subsequent turns and reviewer instructions are retained. Never silently mutate or replace the user's persisted original text, review decisions, or selected source snapshots.
- [App](../src/multi_modal/app.py): user-confirmed web research is added as clearly labeled untrusted evidence only if the user chooses to include it; the app previews the exact selected Git files. Any future compaction of user-selected material must be separately previewed and approved.
- [GPU optimizer](../scripts/gpu_model_optimizer.py) benchmarks GPU-only prompt/decode throughput over context/batch settings; this is **not** a token-economy or QA benchmark.
- [Prompt QA status](PROMPT_QA_STATUS.md) reports a desktop live run with **4/10** passing automated cases and **four empty answers**; updated 12-case full-system QA was pending in the documented environment. Scripted tests passing does not prove live Qwen quality. **Do not shorten output caps blindly.**

## Ranked synthesis

1. **First — measurement and reasoning-mode capability probe (Q01/S01).** The existing four empty Qwen answers make answer completeness and JSON validity more important than an aggressive percentage target. Test `reasoning_effort: "none"`, `chat_template_kwargs: {"enable_thinking": false}`, and server-level `--reasoning off` **as separate version-gated experiments**. The last is an operator-level/server-wide change, not a safe automatic per-request fallback. Also evaluate native `--reasoning-budget` only with explicit quality checks.
2. **Second — zero-new-dependency token-aware context policy (L05/L06, then L01/L03/L04).** Keep raw history immutable. Only compress material after a *visible* preview and user approval; exclude selected Git file snapshots, code, patches, exact user requirements, safety signals and Codex reviewer text from automatic reduction. Preserve web-research provenance and untrusted labeling.
3. **Third — exploit/measure existing llama.cpp prefix reuse (L07/S03).** Stable system prompts and append-only turns aid cache hits. The default already enables caching, so the initial work is instrumentation and avoiding accidental cache misses, not enabling an assumed missing feature. Measure `cached_tokens`, `prompt_n` / `cache_n` when reported and cold/warm time-to-first-token.
4. **Fourth — hardware-only latency/memory experiments (L09/L10/S02/S03).** KV quantization, flash attention, speculative decoding and alternate serving stacks are distinct from token optimization. They belong behind empirical GPU/quality/rollback gates and operator control.
5. **Future multimodal input — no image/video optimization yet.** Qwen3.5 is vision-language capable and its card documents video frame sampling options, but this repository's current message transport is text-first. If typed media is added later, add *separate* image resolution/frame-rate token budgets, fidelity tests and an explicit user-preview/consent boundary; do not retrofit undocumented multimodal token accounting now.

## Minimum experimental matrix (hypotheses, NOT results)

| Controlled arm | Other conditions held constant | Primary metric | Quality/safety gate |
| --- | --- | --- | --- |
| A. Existing deployed baseline | Exact model ID + GGUF quant + llama.cpp build + context + sampling + GPU | Prompt/completion tokens, empty final answers, schema validity, p50/p95 latency | Reproduce 12-case QA, record missing metrics explicitly |
| B. Triaging without reasoning | As A; only mode changes, only Qwen triage | Completion tokens, schema-repair rate, time-to-answer | Same validated fields, confidence/risk/escalation decisions; zero new empty completions |
| C. Low-risk general Qwen without reasoning | As A; no changing GLM or difficult coding/review tasks | Completion tokens and wall time | Same 10 QA case rubric plus manual correctness review |
| D. Approved context compaction | As A; user sees exact proposed vs raw context | Prompt token ratio, grounding/faithfulness | No omissions of paths, quotes, untrusted boundaries, review notes, adverse prompt-injection tests |
| E. Warm vs cold prompt cache | Same request sequence and server; record slot/config/build | Cache hit/processed token counts, TTFT and latency | No cross-task leak; quality invariants with possible non-bitwise-identical logits |
| F. GPU-only memory knobs | Same GGUF, workload, hardware, one knob at a time | VRAM, prompt/decode tok/s, tail latency | No degradation in 12-case QA; record offload proof and rollback |

**Provisional success criteria** (must be validated on this host): zero new empty user-facing responses; no worse structured triage/risk routing or per-case rubric failures; a measurable token reduction on the specific class of prompts subjected to optimization; and positive median latency change **separately** from token savings. Do not call a benchmark successful because `max_tokens` was lowered, text was truncated, or an answer was skipped.
